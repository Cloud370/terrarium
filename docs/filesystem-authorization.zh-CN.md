# 文件系统访问与写入预授权

状态：已实现。本文档是文件系统访问与写入预授权的规范契约，`protocol.md` 与 `security.md` 是它的摘要。它取代了早前基于挂载的授权模型。

## 1. 范围

Terrarium 为模型编写的 JavaScript 提供一个小型文件系统 API。本提案定义一个更简单的目标契约：

- 程序直接使用用户的绝对路径；
- 读取使用操作系统用户可读的文件系统视图；
- 写入要么被拒绝，要么作为一个精确的逐运行文件集合被预授权，要么被操作者声明的写入范围覆盖，要么在显式的完全访问模式下被允许；
- 任何用户决策都发生在 QuickJS 启动之前；
- 实际的写入调用仍由可信宿主检查；
- 模型通过位于每条 user 角色消息头部的一个很小的运行时状态块接收当前宿主状态；
- 系统提示词在所有模式下都以同一个字节稳定的前缀开始。

本版本没有进程、shell、命令或独立网络能力。它不为尚未安装的能力设计占位符。

## 2. 第一性原理

本设计遵循以下规则：

1. 模型提出源代码和请求的写入目标。它不给自己授予权限。
2. 可信宿主拥有调用模式、解析后的路径、批准结果和实际的文件系统效果。
3. 执行前批准，比为等待用户输入而挂起一个正在运行的 JavaScript 运行时更简单。
4. 预授权消除了运行时交互，但它永远不能替代对实际宿主调用的检查。
5. 一个文件系统路径对用户、模型和面向宿主的 API 应当含义相同。
6. 运行时事实比核心指令变化得更频繁，并且不得改变稳定的提示词前缀。
7. 没有当前消费者的机制被排除在外。

因此，本提案没有虚拟路径命名空间、挂载、按目录策略存储、持久权限数据库、运行时授权等待、模型自选模式、模型可请求的写入范围、静态 JavaScript 分析，也没有通用的能力授权框架。唯一的递归写入范围是操作者在启动参数中声明的。

## 3. 路径与工作根

每个 `host.fs` 路径都是用户的绝对路径。没有 `/workspace` 别名，也没有 `virtual=real` 映射。相对路径和 `~` 展开会被拒绝。

`working_root` 是与 agent 会话关联的稳定目录；对直接运行而言则是进程工作目录。它对模型是有用的上下文，但它不是命名空间，本身既不授予也不限制访问。

例如，当工作根是 `/code/terrarium` 时，模型会这样使用：

```js
const cargo = host.fs.text("/code/terrarium/Cargo.toml");
```

它永远不需要把该路径转换成一个合成名称。

所有模式下的读取都使用操作系统用户可读的视图。读取失败仍然是可观察的宿主错误。程序可以把读到的数据放进模型可见的 facts，因此选择模型供应商也就同时选择了程序所读数据的信任边界。本提案有意不把宽泛的读取描述为数据隔离。

## 4. 调用模式

受信任的调用者为一次调用恰好选择一个文件系统模式：

| 模式 | 读取 | 写入 | 用户交互 |
|---|---|---|---|
| `read-only` | 操作系统可读的绝对路径 | 一律拒绝 | 无 |
| `planned-write` | 操作系统可读的绝对路径 | 本次运行批准的精确文件，加上操作者声明的范围 | 对未被覆盖的被请求目标，执行前一次决策 |
| `full-access` | 操作系统可读的绝对路径 | 操作系统用户允许的任意绝对路径 | 无 |

`planned-write` 是模型驱动 agent 的默认模式。`read-only` 是硬性拒绝，不是模型可以提升的模式。`full-access` 是操作者的显式选择，面向受信任的 CLI 与调试工作流。

在 `planned-write` 中，操作者可以在启动时用可重复的 `--allow-write DIR|FILE` 授予递归写入范围。`FILE` 参数精确匹配该解析后的文件；`DIR` 参数匹配其下的每个路径。被授予的范围无需提示即加入每次运行的冻结写入权限，它们覆盖的被请求目标永远不会到达用户提示。模型不能请求、扩大或发现这些范围：access 块只声明精确文件，运行时状态也不列出已授予的范围——模型总是声明其预期目标，由宿主做覆盖扣除。将 `--allow-write` 与 `--read-only` 或 `--full-access` 同时使用是启动错误。

`full-access` 只适用于已安装的文件系统能力。在本版本中，它不意味着进程执行或独立网络访问，因为这些能力并不存在。

模式是调用局部的。会话日志或历史运行时状态消息不是授权依据，永远不会恢复先前的模式。

## 5. 稳定提示词与运行时状态

### 5.1 稳定前缀

系统提示词以同一个字节稳定的核心前缀开始。模式、路径、时间戳、请求标识符、模型名称、授权结果以及其他运行时取值，一律不得被插值进该前缀。

前缀解释：

- 宿主 API 与运行协议；
- 全部三种文件系统模式；
- 运行时状态块的含义；
- 只有当前宿主状态指定的模式才适用；
- 本版本不安装进程执行能力，也不安装独立网络能力；
- 提示词与模型输出不实施权限。

在同一个提示词协议版本内，既有的前缀字节永不改变。破坏性的指令变更会创建一个新版本，而不是静默改写旧前缀。能力专属的材料可以按确定性顺序追加在稳定前缀之后，而不改变前缀本身。

### 5.2 用户消息渲染

每条新发出的 user 角色消息都是一个文本字符串，其头部是宿主生成的运行时状态块，后接作为 Markdown 的自然用户消息或宿主观察：

```text
user.content = "<terrarium-runtime-state>...</terrarium-runtime-state>\n\n" +
               "用户的 Markdown 或一条宿主观察"
```

协议中立的消息模型保持单一内容字符串，全部三个适配器保持其现有文本编码，不需要多部分内容表示。拼接是确定性的，因此渲染出的消息字节稳定，重试同一个模型请求时复用完全相同的字节。

静态提示词会说明：以宿主状态块开头的消息携带宿主元数据；出现在用户文本其他位置的同名标签只是普通用户文本。这一约定改善模型理解；它不是安全边界。

### 5.3 运行时状态格式

运行时状态是被 XML 包裹的 Markdown，而不是一个 XML 对象模型：

```xml
<terrarium-runtime-state>
### Current runtime
- Working root: `/code/terrarium`
- Filesystem mode: `planned-write`
- Installed host capabilities: `host.fs`
</terrarium-runtime-state>
```

宿主拥有其中每个值，并对可能闭合包装标签的文本进行转义。字段使用固定名称和确定性顺序。该状态不包含时间戳、随机标识符、耗时计数器，或任何其他改变了却不影响模型行为的值。在二进制生命周期内永不变化的事实——例如不存在进程或网络能力——在稳定前缀中说明一次，而不是逐消息重复。

每条新发出的 user 角色消息都包含一份完整的状态快照，包括模型步骤之间的宿主观察。状态未变化时，渲染出的块在字节上完全相同。状态变化时，宿主发出一份新快照，而从不改写历史消息。最新快照是当前的；较早的快照只是历史上下文。

这既保留了上一次模型调用所使用的请求前缀，又让每个新步骤自描述。

## 6. 写入访问请求

### 6.1 响应形态

本设计有意避免 `plan` 这个词，因为模型也可能产出实现计划或推理计划。写入访问请求是一个范围很窄的预授权协议。

每个由模型选定的运行都是一个闭合的 `run` 块，其前可选地有一个闭合的 `access` 块；任何其他排列都是协议错误：

````text
```access
{"writes":["/code/terrarium/src/fs.rs","/code/terrarium/tests/library_api.rs"],"reason":"Update filesystem authorization and its regression tests"}
```
```run
const source = host.fs.text("/code/terrarium/src/fs.rs");
host.fs.write("/code/terrarium/src/fs.rs", update(source));
return {to: "model", facts: {updated: true}};
```
````

提示词指示模型总是发出 `access` 块，即使是空形式，使响应习惯成为一条无条件规则。解析器有意比指令更宽容：缺失的 `access` 块等价于空请求，不是协议错误，因为省略一个空声明与做出该声明在语义上完全相同。块之外的文本是展示性的。只有真正的歧义才是协议错误：没有 `run` 块、存在未闭合的块、`access` 块出现在 `run` 块之后、多于一个 `access` 块、多于一个 `run` 块，或 access JSON 无效。

`access` 的值是严格 JSON，恰好两个字段：

```text
writes: 精确绝对文件路径组成的数组
reason: 一条面向用户的简短字符串
```

不需要预授权时，模型发出固定的空形式：

```json
{"writes":[],"reason":""}
```

该请求是给宿主的数据。它不是 JavaScript、不是工具调用、不是通用任务计划，也不是权限授予。

### 6.2 按模式区分的含义

每种模式都使用同一个响应文法：

| 当前模式 | `writes` 值 | 宿主行为 |
|---|---|---|
| `read-only` | 空；非空请求是供纠正的反馈，JavaScript 不启动 | 在硬性写入拒绝下运行 |
| `planned-write` | 程序可以写入的精确文件；仅检查的运行为空 | 对未被操作者范围覆盖的被请求目标，执行前询问一次 |
| `full-access` | 任意值；非空列表作为声明意图入日志，权限上被忽略 | 以完整文件系统写入权限运行，不提示 |

在 `planned-write` 中，当 `writes` 非空时必须有非空的 `reason`。reason 只是展示文本，它永远不改变哪些路径被授权。

在 `full-access` 中，声明集合仍随运行记录：之后把它与已提交的写入回执对比，是发现异常行为的审计信号，永远不是执行机制。

### 6.3 路径请求规则

每个被请求的目标必须是：

- 一个绝对文件路径；
- 不含 `.` 和 `..` 组件，也不含有歧义的分隔符；
- 一个精确路径，而不是目录、glob、前缀或递归范围；
- 在宿主规范化后唯一。

目标可以是已存在的文件，也可以是新文件。批准一个新文件目标，即把为该次写入创建其缺失父目录链包含在该批准之内；批准展示会标出父目录尚不存在的目标。目录创建永远不把权限扩展到其他任何路径：已创建目录中的另一个文件仍需要自己的批准。

已存在的符号链接目标在写入时会被拒绝。父路径别名由宿主在展示与批准之前解析。规范化是平台感知的：macOS 的 `/tmp` 别名，以及 Windows 盘符大小写与分隔符形态，都必须在唯一性与成员判定之前归并为同一身份。

宿主将请求限制为至多 32 条路径、4 KiB 编码大小和 200 字符的 reason。无效或超大的请求是协议错误，JavaScript 不会启动。

## 7. 预授权生命周期

对 `planned-write` 而言，完整生命周期是：

```text
模型响应
    -> 解析一个可选的 access 块和恰好一个 run 块
    -> 校验并解析每个被请求的路径
    -> 扣除被操作者声明范围覆盖的目标
    -> 向用户展示剩余集合与理由
    -> 用户以一次决策允许或拒绝该集合
    -> 冻结本次运行的写入范围：操作者范围加上已批准的精确路径
    -> 启动 QuickJS
    -> 每个实际写入都对照该冻结范围检查
```

如果扣除之后没有剩余，不发生提示，运行直接启动。

用户的决策只有：

```text
allow
deny
```

不支持部分批准。更改任何被请求的路径都需要一次新的模型响应和一次新的决策。拒绝会终止整个运行，包括操作者范围本可覆盖的目标；模型可以在新响应中仅重新请求被覆盖的子集，这不会触发提示。批准只作用于相关联的运行，并在该运行结束时被丢弃。

用户交互是一个显式的、由适配器拥有的接口，绝不是内核行为：

```rust
trait Authorizer {
    fn decide(&self, request: &ResolvedAccessRequest) -> Decision;
}

enum Decision { Allow, Deny, Cancel, Unavailable }
```

终端适配器实现一次决策提示。没有交互授权者的调用——管道、CI 任务或后台运行——实现 `unavailable`。内核只接收冻结的权限，从不渲染提示。

如果请求被拒绝、被取消，或没有可用的授权者，JavaScript 不会启动。外层 agent 收到一个有界的结构化结果——`authorization_denied`、`authorization_cancelled` 或 `authorization_unavailable`——模型观察会说明未被授权的解析后集合、决策结果，以及下一步：本 turn 内不要重新请求同一集合；继续只读或转交用户。unavailable 变体说明本次调用无法授权任何写入。

本版本不缓存拒绝决策；观察措辞是唯一的循环防护。如果之后的持久日志显示模型反复重新请求同一个被拒集合，可以在适配器内部加入 turn 内抑制，而不改变本接口。

QuickJS 内部没有等待中的授权、没有暂停的执行预算、没有可恢复的续点，也没有运行时授权超时。普通的运行超时只在预授权成功并且 QuickJS 启动之后才开始。

## 8. 运行时实施

预授权确定一个最大写入范围；它并不信任程序会遵守自己的声明。

每次 `host.fs.write` 和 `host.fs.replace` 调用都使用 JavaScript 实际提供的路径：

```text
实际写入调用
    -> 校验绝对路径语法
    -> 解析既有的父目录与目标状态
    -> 应用调用模式
    -> 在 planned-write 中，要求目标匹配某个冻结范围：
       一个已批准的精确路径，或一个操作者声明的前缀
    -> 复查符号链接与父目录条件
    -> 执行原子写入，按批准创建缺失的父目录
    -> 记录普通写入回执
```

模式实施是确定性的：

- `read-only` 对每次写入都返回 `write_denied`；
- 当实际目标不匹配任何冻结范围时，`planned-write` 返回 `write_not_authorized`；
- `full-access` 跳过范围成员检查，但保留路径校验和操作系统权限检查。

未声明的路径永远不会触发第二次提示。JavaScript 可以捕获该错误，但换一种拼写、一个符号链接或另一个宿主函数都无法扩大冻结范围。

批准是路径授权，不是内容审查。目标被批准后，程序可以向该精确目标写入任何有界的文本内容。未来的 diff 预览将是一个用户界面特性，不属于这个权限模型。

多个被批准的写入不是一个事务。如果后续写入失败，先前已提交的写入仍然保留。宿主导出的写入回执继续描述已提交的写入；它们不是回滚日志。

读取操作在今天为同步之处仍保持为同步的宿主操作。写入操作不需要为了授权而变成可 await 的，因为用户交互在 QuickJS 启动之前已经完成。既有的异步 scan 与 walk 迭代保持不变。

宿主继续拥有常规文件检查、解码规则、有界读取、遍历行为、原子替换、输出上限、取消和回执。本运行时不声称能够击败在检查间隙替换文件系统对象的恶意并发进程；那需要本设计之外的操作系统隔离边界。

## 9. 会话、恢复与权限

运行时状态快照可以出现在持久的模型可见历史中，以便后续请求保留精确的消息前缀。它始终是历史文本，不是授权依据。恢复时，受信任的调用者重新选择一个调用模式，下一条 user 角色消息携带该当前状态。

每个访问请求及其决策都作为一条有界的 `run/access` 事件入日志，记录解析后的路径、理由和决策——包括在 `full-access` 下被接受并忽略的声明。日志是审计记录，永远不是授权依据。

写入访问请求及其批准是运行局部的。第一个版本不持久化可复用的授权、等待中的批准、ACL 数据库或权限注册表。已启动但没有持久结果的运行保持为 `outcome_unknown`，且永远不会被自动重放。

以下不变量成立：

- 必需的访问请求获得批准之前，任何 JavaScript 都不启动；
- 不会在模式实际权限之外的路径产生任何效果；
- 执行前的拒绝或取消不会产生任何程序文件系统效果；
- 恢复逻辑至多执行一次已批准的程序；
- 历史提示词文本永远不会恢复权限。

## 10. 目标架构

最小化的受信任类型在概念上是：

```rust
enum FilesystemMode {
    ReadOnly,
    PlannedWrite,
    FullAccess,
}

enum WriteScope {
    Exact(ResolvedPath),  // 由用户为一次运行批准
    Prefix(ResolvedPath), // 由操作者在启动时声明
}

enum RunFilesystemAuthority {
    ReadOnly,
    Scoped(Vec<WriteScope>),
    FullAccess,
}
```

外层 agent 适配器解析模型响应，并通过 `Authorizer` 获取所需的任何用户决策。可复用的内核只接收源代码加上宿主导出的 `RunFilesystemAuthority`；它不解析模型散文，也不实现用户界面。

实现方向是：

1. 把运行时状态渲染为确定性的、由宿主前置的文本块，置于现有单一字符串消息内容之内；适配器保持其当前文本编码。
2. 把提示词拆分为不可变的核心前缀和由宿主渲染的运行时状态。
3. 为 run 块解析器扩展一个可选的 access 块：缺失即空请求，每种块至多一个，周边文字保持展示性。
4. 用调用文件系统模式加操作者 `--allow-write` 范围替换公开的 `Mount` 输入；对一次运行，使用精确的已批准路径集合。
5. 用直接的绝对路径校验与平台感知的规范化替换挂载解析。
6. 移除 `--mount`；保留显式的 `--read-only` 与 `--full-access`；新增可重复的 `--allow-write DIR|FILE`，仅在 `planned-write` 中有效；`planned-write` 保持为模型驱动的默认值。
7. 在调用内核之前，在外层适配器中通过 `Authorizer` 接口执行 planned-write 批准，并把每次 `run/access` 决策入日志。
8. 在 `write` 与 `replace` 之间共享同一个范围成员检查，并保留写入回执。
9. 在同一个契约版本中更新提示词、registry 文本、会话投影、CLI 输出、测试和规范性文档。

对直接 `terrarium run` 而言，最小且有用的选择是：默认只读，显式 `--full-access` 用于受信任的调试；`--allow-write` 范围对操作者编写的程序同样可用。它没有可以预授权路径的模型 access 块。

## 11. 明确的非目标与未来扩展

本版本不实现、也不规定进程执行、shell 命令、子进程、独立网络请求、持久授权、按目录策略、模型可请求的通配符或前缀写入范围、部分批准、内容批准、事务、回滚或拒绝缓存。

如果未来版本安装进程或网络能力，它可以复用请求、预授权与确定性宿主检查这一外层序列。它必须添加能力专属的运行时状态字段、请求记录和匹配器。文件路径、进程 spawn 和网络请求不是可以互换的授权对象。

未来的进程请求至少需要匹配解析后的可执行文件、完整 argv、cwd 和环境策略。未来的网络请求至少需要匹配 scheme、host、port、method、path、重定向策略和出站数据策略。二者都不应仅因为文件系统模式是 `full-access` 就继承权限。

这类新增必须保留既有的稳定提示词前缀，或引入一个单独编号的后继版本。在能力存在之前，它们不应当向当前 access 块添加投机性的字段。
